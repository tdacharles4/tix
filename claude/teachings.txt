TASK #16 — CHECK-IN SESSION SYSTEM (SCANNER AUTH)
================================================================================
Last updated: 2026-07-05
Scope: Per-organizer scanner subaccounts. Custom JWT auth. Mobile-only access
at scan.boleteo.com. Two panels: live dashboard (pie chart + guest list) and
camera QR reader. Organizers create, manage, and delete scanner accounts from
their main dashboard.

This file is the canonical implementation plan. Read it fully before touching
any code. Each phase builds on the previous one — do not skip ahead.


================================================================================
ARCHITECTURE OVERVIEW
================================================================================

WHY CUSTOM JWT (not Supabase Auth)
────────────────────────────────────────────────────────────────
Scanner accounts are not real users. They have no email, no personal data,
no ability to reset their own password, and no access to anything outside
the scanner panel. Supabase Auth is overkill — it would create rows in
auth.users, trigger email verification flows, and introduce unnecessary
surface area.

Custom JWT approach:
  - Organizer creates scanner accounts (username + hashed password) in a
    scanner_accounts table
  - On login, server verifies password, issues a signed JWT in an httpOnly cookie
  - Middleware validates the cookie on every request to scanner routes
  - Token carries { scanner_id, organizer_id } — all the context needed

WHY httpOnly COOKIE (not localStorage or Authorization header)
────────────────────────────────────────────────────────────────
httpOnly cookies:
  - Cannot be read by JavaScript (XSS-proof)
  - Sent automatically on every request (no client-side token management)
  - Works with Next.js middleware (middleware reads cookies, not headers)
  - Correct for browser-based apps where the client and API share a domain

localStorage would require manually attaching a token to every fetch call
and is readable by any JavaScript on the page.

WHY SUBDOMAIN (scan.boleteo.com, not /scan route)
────────────────────────────────────────────────────────────────
Two reasons:

1. Psychological separation. Door staff should have no way to accidentally
   navigate to the organizer dashboard or buyer-facing pages. A subdomain
   makes the scanner panel feel like a distinct tool.

2. Cookie scoping. Cookies can be scoped to a subdomain. The scanner JWT
   cookie is set with Domain=scan.boleteo.com — it will never be sent to
   requests on boleteo.com. The organizer's Supabase session cookie will
   never be sent to scan.boleteo.com. Clean separation by default.

In Next.js + Vercel, both boleteo.com and scan.boleteo.com point to the
same deployment. Middleware reads req.nextUrl.hostname and handles routing.
No separate Next.js app or repo needed.

WHY MOBILE-ONLY
────────────────────────────────────────────────────────────────
The scanner panel is designed for a door staff member holding a phone and
scanning QR codes. A desktop layout is not designed, not tested, and
would create a confusing experience. Middleware enforces mobile-only by
reading the User-Agent header. Desktop browsers get a static redirect page.

SCANNER ACCOUNT SCOPE: PER-ORGANIZER (not per-event)
────────────────────────────────────────────────────────────────
Scanner accounts belong to an organizer, not to a specific event. This
means door staff don't need a new account for every event. Instead they
log in, see a list of the organizer's live/upcoming events, pick the one
they're working, and proceed.

Trade-off: a scanner account can theoretically scan for ANY of the
organizer's events. This is acceptable — if the organizer trusts someone
with their scanner credentials, they trust them across their events. If
finer-grained control is needed later, add an event_ids allowlist column
to scanner_accounts.

PHASE 1 — SCHEMA
================================================================================
Run in Supabase SQL editor.

────────────────────────────────
Block 1: scanner_accounts table
────────────────────────────────

  CREATE TABLE scanner_accounts (
    id           uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    organizer_id uuid        NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    username     text        NOT NULL,
    password_hash text       NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE(organizer_id, username)
  );

  -- Organizers can only see and manage their own scanner accounts
  ALTER TABLE scanner_accounts ENABLE ROW LEVEL SECURITY;

  CREATE POLICY "Organizers manage their own scanner accounts"
    ON scanner_accounts
    FOR ALL
    USING (organizer_id = auth.uid())
    WITH CHECK (organizer_id = auth.uid());

Why UNIQUE(organizer_id, username)?
  Two organizers can both have a scanner named "puerta1" — that's fine.
  One organizer cannot have two scanners with the same username — that
  would create ambiguity at login (which one do you authenticate?).

Why ON DELETE CASCADE?
  If an organizer account is deleted, their scanner accounts go with it.
  Orphaned scanner accounts that reference a deleted organizer are useless
  and would hold a bcrypt hash with no associated context.

Why store password_hash and not password?
  Passwords are never stored in plaintext. Ever. bcryptjs produces a hash
  that cannot be reversed to the original password. Authentication works
  by re-hashing the submitted password and comparing hashes.

Why RLS on this table?
  Organizers list/create/delete their own scanner accounts from the
  organizer dashboard (authenticated via Supabase Auth). RLS ensures
  an organizer cannot accidentally view or delete another organizer's
  scanner accounts even if there's a bug in the API layer.

  Note: the scanner login API route uses createServiceClient() (service role,
  bypasses RLS) because the scanner is not a Supabase Auth user — there is
  no auth.uid() to match against when a scanner logs in.

PHASE 2 — PACKAGES + ENV VARS
================================================================================

Install:
  npm install bcryptjs jose html5-qrcode
  npm install --save-dev @types/bcryptjs

  bcryptjs  — Pure JS bcrypt implementation. No native bindings — works in
              Next.js Node.js runtime without compilation issues. Used for
              password hashing and comparison.

  jose      — JavaScript JWT library. Supports Edge Runtime (unlike jsonwebtoken
              which requires Node.js crypto module). Used to sign and verify the
              scanner JWT. This is the library Next.js Auth.js uses internally.

  html5-qrcode — Camera-based QR code scanner for mobile browsers. Wraps the
                 device camera API and decodes QR codes in real time. Works on
                 iOS Safari (requires HTTPS in production) and Android Chrome.
                 Alternative: @zxing/browser (heavier, more formats). html5-qrcode
                 is simpler and sufficient for QR-only use.

Env vars to add to .env.local:
  SCANNER_JWT_SECRET=<random string>
    Generate with: openssl rand -hex 32
    Used to sign and verify scanner JWTs. Server-only — never prefix NEXT_PUBLIC_.
    If this secret is rotated, all active scanner sessions are invalidated
    (all door staff will need to log in again). Treat it like a password.

  ⚠️ WINDOWS NOTE: If switching to a Windows machine, .env.local must be
  manually created in the project root. Windows does not read it automatically
  in all shell environments. Confirm Next.js picks up all variables on first run
  by checking that the app boots without "X is not set" errors.

PHASE 3 — AUTH INFRASTRUCTURE
================================================================================

────────────────────────────────
3a. lib/scanner/password.ts
────────────────────────────────
Pure utility functions — no framework dependencies.

  import bcrypt from 'bcryptjs';

  const SALT_ROUNDS = 12;

  export async function hashPassword(password: string): Promise<string> {
    return bcrypt.hash(password, SALT_ROUNDS);
  }

  export async function verifyPassword(
    password: string,
    hash: string,
  ): Promise<boolean> {
    return bcrypt.compare(password, hash);
  }

Why SALT_ROUNDS = 12?
  bcrypt's cost factor is exponential — rounds=12 means 2^12 = 4096 hashing
  iterations, taking ~250ms on modern hardware. This makes brute-force attacks
  impractical: an attacker trying 1 million passwords would need ~70 hours.
  rounds=10 (bcrypt default) is acceptable; 12 is the current security
  recommendation for 2025+. Do not go above 14 without benchmarking — it
  will make your login endpoint noticeably slow.

────────────────────────────────
3b. lib/scanner/jwt.ts
────────────────────────────────

  import { SignJWT, jwtVerify } from 'jose';

  const SECRET = new TextEncoder().encode(process.env.SCANNER_JWT_SECRET!);
  const EXPIRY = '8h';

  export type ScannerJWTPayload = {
    scanner_id: string;
    organizer_id: string;
  };

  export async function signScannerToken(payload: ScannerJWTPayload): Promise<string> {
    return new SignJWT(payload)
      .setProtectedHeader({ alg: 'HS256' })
      .setIssuedAt()
      .setExpirationTime(EXPIRY)
      .sign(SECRET);
  }

  export async function verifyScannerToken(
    token: string,
  ): Promise<ScannerJWTPayload | null> {
    try {
      const { payload } = await jwtVerify(token, SECRET);
      return payload as unknown as ScannerJWTPayload;
    } catch {
      return null; // expired, tampered, or malformed
    }
  }

Why 8h expiry?
  A typical event runs 4–6 hours. 8h covers setup, the event, and teardown
  without forcing door staff to re-authenticate mid-event. Shorter expiry
  (1h) would cause frustrating login loops. Longer (24h) is unnecessarily
  permissive. 8h is the right balance.

Why HS256 (symmetric) and not RS256 (asymmetric)?
  RS256 requires a public/private key pair. It's valuable when multiple
  services need to verify the token independently (microservices). Here,
  all verification happens in one Next.js app. HS256 with a strong secret
  is simpler and equally secure for this use case.

────────────────────────────────
3c. lib/scanner/cookies.ts
────────────────────────────────

  import { cookies } from 'next/headers';

  export const SCANNER_COOKIE = 'scanner_token';

  export function setScannerCookie(token: string) {
    cookies().set(SCANNER_COOKIE, token, {
      httpOnly: true,
      secure:   process.env.NODE_ENV === 'production',
      sameSite: 'strict',
      maxAge:   8 * 60 * 60, // 8 hours in seconds
      path:     '/',
    });
  }

  export function clearScannerCookie() {
    cookies().set(SCANNER_COOKIE, '', {
      httpOnly: true,
      secure:   process.env.NODE_ENV === 'production',
      sameSite: 'strict',
      maxAge:   0,
      path:     '/',
    });
  }

Why secure: true only in production?
  secure: true requires HTTPS. In local development, Next.js runs on HTTP
  (localhost). Setting secure: true locally would prevent the cookie from
  being set at all, breaking local testing. In production on Vercel, all
  traffic is HTTPS, so secure: true is enforced there.

Why sameSite: 'strict'?
  Prevents the cookie from being sent on cross-site requests (CSRF attacks).
  Since the scanner panel is a standalone tool accessed directly, strict is
  appropriate. If you ever need to embed the scanner in an iframe from another
  domain, change to 'lax'.

PHASE 4 — API ROUTES (AUTH)
================================================================================

────────────────────────────────
4a. POST /api/scanner/login
────────────────────────────────

  // app/api/scanner/login/route.ts
  import { NextRequest, NextResponse } from 'next/server';
  import { createServiceClient } from '@/lib/supabase/server';
  import { verifyPassword } from '@/lib/scanner/password';
  import { signScannerToken } from '@/lib/scanner/jwt';
  import { setScannerCookie } from '@/lib/scanner/cookies';

  export async function POST(req: NextRequest) {
    const { username, password } = await req.json();

    if (!username || !password) {
      return NextResponse.json({ error: 'Missing credentials' }, { status: 400 });
    }

    const supabase = createServiceClient();

    // Look up by username only — no organizer context at login time
    // (username is globally unique per organizer; we identify organizer from the row)
    const { data: account } = await supabase
      .from('scanner_accounts')
      .select('id, organizer_id, password_hash')
      .eq('username', username)
      .single();

    if (!account) {
      // Constant-time failure — don't reveal whether username exists
      await verifyPassword('__dummy__', '$2b$12$invalidhashpadding000000000000000000000000000000000000');
      return NextResponse.json({ error: 'Invalid credentials' }, { status: 401 });
    }

    const valid = await verifyPassword(password, account.password_hash);
    if (!valid) {
      return NextResponse.json({ error: 'Invalid credentials' }, { status: 401 });
    }

    const token = await signScannerToken({
      scanner_id:   account.id,
      organizer_id: account.organizer_id,
    });

    setScannerCookie(token);
    return NextResponse.json({ ok: true });
  }

Why the dummy bcrypt call on username-not-found?
  Without it, an attacker can measure response time to enumerate valid usernames:
  "if this username doesn't exist, the response is fast; if it does, it's slow
  (bcrypt takes 250ms)." The dummy call makes both paths take ~250ms.
  The dummy hash is intentionally invalid — bcrypt.compare returns false,
  and we return 401. No security impact, but timing is equalized.

Why not include the organizer_id in the login request?
  Requiring the organizer_id or a "team code" at login adds friction without
  adding meaningful security (if you have the username and password, you have
  the organizer_id). Simplicity wins here.

PHASE 5 — API ROUTES (SCANNER DATA)
================================================================================

────────────────────────────────
5a. GET /api/scanner/events
────────────────────────────────
Returns the organizer's live and upcoming events. Scanner picks one to work.

  // app/api/scanner/events/route.ts
  import { NextRequest, NextResponse } from 'next/server';
  import { cookies } from 'next/headers';
  import { createServiceClient } from '@/lib/supabase/server';
  import { verifyScannerToken } from '@/lib/scanner/jwt';
  import { SCANNER_COOKIE } from '@/lib/scanner/cookies';

  export async function GET(req: NextRequest) {
    const token = cookies().get(SCANNER_COOKIE)?.value;
    const payload = token ? await verifyScannerToken(token) : null;
    if (!payload) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    const supabase = createServiceClient();

    const { data: events } = await supabase
      .from('events')
      .select('id, title, date, venue, tickets_sold, capacity')
      .eq('organizer_id', payload.organizer_id)
      .in('status', ['live'])
      .order('date', { ascending: true });

    return NextResponse.json({ events: events ?? [] });
  }

Why only 'live' events?
  'draft' events aren't public yet — no tickets have been sold. 'closed',
  'cancelled', and 'finalizado' events are in the past. Door staff only need
  to see events they could be working right now.

────────────────────────────────
5b. GET /api/scanner/[eventId]/guests
────────────────────────────────
Full guest list for an event with real-time scan status.

  // app/api/scanner/[eventId]/guests/route.ts
  import { NextRequest, NextResponse } from 'next/server';
  import { cookies } from 'next/headers';
  import { createServiceClient } from '@/lib/supabase/server';
  import { verifyScannerToken } from '@/lib/scanner/jwt';
  import { SCANNER_COOKIE } from '@/lib/scanner/cookies';

  export async function GET(
    req: NextRequest,
    { params }: { params: { eventId: string } }
  ) {
    const token = cookies().get(SCANNER_COOKIE)?.value;
    const payload = token ? await verifyScannerToken(token) : null;
    if (!payload) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });

    const supabase = createServiceClient();

    // Verify this event belongs to the scanner's organizer
    const { data: event } = await supabase
      .from('events')
      .select('id, organizer_id, title, capacity')
      .eq('id', params.eventId)
      .eq('organizer_id', payload.organizer_id)
      .single();

    if (!event) return NextResponse.json({ error: 'Event not found' }, { status: 404 });

    const { data: tickets } = await supabase
      .from('tickets')
      .select('id, holder_name, ticket_type, status, redeemed_at')
      .eq('event_id', params.eventId)
      .in('status', ['active', 'redeemed'])
      .order('holder_name', { ascending: true });

    const total    = tickets?.length ?? 0;
    const scanned  = tickets?.filter(t => t.status === 'redeemed').length ?? 0;

    return NextResponse.json({
      event: { id: event.id, title: event.title, capacity: event.capacity },
      summary: { total, scanned, remaining: total - scanned },
      tickets: tickets ?? [],
    });
  }

Why verify event.organizer_id === payload.organizer_id?
  Defense in depth. Without this check, a compromised scanner token could
  request guest lists for events belonging to other organizers. The check
  ensures a scanner can only access data for their own organizer's events,
  even if the JWT is stolen.

Why filter status IN ('active', 'redeemed') and not just all tickets?
  'cancelled' and 'transferred' tickets should not appear on the guest list —
  they're no longer valid. Only active (not yet scanned) and redeemed (already
  scanned) tickets represent real attendees.

PHASE 6 — MIDDLEWARE UPDATES
================================================================================

Update the existing middleware.ts (or create it if it doesn't exist).
The middleware handles THREE distinct concerns:

  1. Subdomain detection — am I on scan.boleteo.com?
  2. Mobile enforcement — is this a mobile browser?
  3. Scanner JWT validation — is the scanner logged in?

  // middleware.ts
  import { NextRequest, NextResponse } from 'next/server';
  import { verifyScannerToken } from '@/lib/scanner/jwt';
  import { SCANNER_COOKIE } from '@/lib/scanner/cookies';

  const MOBILE_REGEX = /Android|iPhone|iPad|iPod|Mobile/i;
  const SCANNER_HOST = 'scan.boleteo.com';

  export async function middleware(req: NextRequest) {
    const host      = req.nextUrl.hostname;
    const pathname  = req.nextUrl.pathname;
    const ua        = req.headers.get('user-agent') ?? '';
    const isMobile  = MOBILE_REGEX.test(ua);
    const isScanner = host === SCANNER_HOST || host === 'scan.localhost';

    // ── Scanner subdomain ──────────────────────────────────────────────────
    if (isScanner) {
      // Mobile check first
      if (!isMobile && pathname !== '/scan/desktop-only') {
        return NextResponse.redirect(new URL('/scan/desktop-only', req.url));
      }

      // Let login and desktop-only pages through unauthenticated
      if (pathname === '/scan/login' || pathname === '/scan/desktop-only') {
        return NextResponse.next();
      }

      // All other scanner routes require a valid JWT
      const token   = req.cookies.get(SCANNER_COOKIE)?.value;
      const payload = token ? await verifyScannerToken(token) : null;

      if (!payload) {
        return NextResponse.redirect(new URL('/scan/login', req.url));
      }

      return NextResponse.next();
    }

    // ── Main domain — block /scan/* routes ────────────────────────────────
    if (pathname.startsWith('/scan/')) {
      return NextResponse.redirect(new URL('/', req.url));
    }

    // ── Existing main-domain middleware logic (Supabase auth, etc.) ────────
    // ... your existing middleware code here ...

    return NextResponse.next();
  }

  export const config = {
    matcher: [
      '/((?!_next/static|_next/image|favicon.ico).*)',
    ],
  };

Local development note on subdomains:
  `scan.localhost` resolves to 127.0.0.1 in most browsers without any host
  file changes. Test locally by visiting http://scan.localhost:3000/scan/login.
  If the browser doesn't resolve scan.localhost, add to /etc/hosts (Mac/Linux)
  or C:\Windows\System32\drivers\etc\hosts (Windows):
    127.0.0.1 scan.localhost

  The middleware checks for both 'scan.boleteo.com' (production) and
  'scan.localhost' (development) — remove 'scan.localhost' before launch.

Why read User-Agent in middleware (not in the page)?
  If the check is in the page, the desktop user loads the full page bundle,
  React hydrates, then a redirect fires. That's a flash of wrong content.
  Middleware runs on the edge before any content is served — the redirect
  is instant and no scanner UI code is ever delivered to a desktop browser.

Why is verifyScannerToken async in middleware?
  jose's jwtVerify is async (it uses the Web Crypto API, which is async
  by spec). This is fine — Next.js middleware supports async functions.

TAB: CAMERA
────────────────
Uses html5-qrcode to open the device camera and decode QR codes.

IMPORTANT: html5-qrcode manipulates the DOM directly and is not a React
component. Use it inside a useEffect with a cleanup function:

  const scannerRef = useRef<Html5Qrcode | null>(null);

  useEffect(() => {
    if (tab !== 'camera') return;

    const qr = new Html5Qrcode('qr-reader');
    scannerRef.current = qr;

    qr.start(
      { facingMode: 'environment' },  // back camera
      { fps: 10, qrbox: { width: 250, height: 250 } },
      async (decodedText) => {
        // decodedText is the ticket UUID
        await qr.stop();
        await handleScan(decodedText);
      },
      undefined // error callback — ignore decode misses
    );

    return () => {
      qr.stop().catch(() => {});
    };
  }, [tab]);

  async function handleScan(ticketId: string) {
    const res = await fetch(`/api/tickets/${ticketId}/validate`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ scanned_by: 'scanner' }),
    });
    const data = await res.json();
    setScanResult(data);   // show result overlay
  }

The existing /api/tickets/[id]/validate route already returns the reason
for failure (not_found, wrong_event, already_redeemed, etc.) — use that
to drive the overlay content.

8a. API routes (main domain, Supabase auth)
────────────────────────────────

These routes use the regular Supabase auth (organizer session), not the
scanner JWT. All four are under /api/organizer/scanners/.

GET /api/organizer/scanners
  Returns list of scanner accounts for the logged-in organizer.
  SELECT id, username, created_at (NEVER password_hash).

POST /api/organizer/scanners
  Body: { username: string, password: string }
  Validate: username 3–30 chars, alphanumeric + underscores only.
  Validate: password minimum 8 chars.
  Hash password with hashPassword(), insert row.
  Return: { id, username, created_at }
  Error on UNIQUE violation: "Ya existe un escáner con ese nombre"

PATCH /api/organizer/scanners/[id]
  Body: { password: string }
  Hash new password, update password_hash where id = [id] AND organizer_id = user.id.
  The organizer_id check prevents an organizer from changing another's scanner password.
  Return: { ok: true }

DELETE /api/organizer/scanners/[id]
  Delete where id = [id] AND organizer_id = user.id.
  Return: { ok: true }

PHASE 9 — VERCEL SUBDOMAIN CONFIGURATION
================================================================================
This phase is infrastructure, not code. Do it after all code is deployed.

In Vercel project settings → Domains:
  Add domain: scan.boleteo.com
  This creates a CNAME record pointing scan.boleteo.com to your Vercel deployment.
  The same Next.js app serves both boleteo.com and scan.boleteo.com.
  Middleware handles the routing split.

In your DNS provider (wherever boleteo.com is registered):
  Add CNAME record:
    Name: scan
    Value: cname.vercel-dns.com (or whatever Vercel specifies)
    TTL: 3600

SSL:
  Vercel automatically provisions an SSL certificate for scan.boleteo.com
  via Let's Encrypt. No manual SSL setup needed.

Testing before DNS propagates:
  Deploy the code first. Test via the Vercel preview URL (e.g., your-app.vercel.app).
  Middleware hostname check won't match in preview — temporarily add the preview
  hostname to the isScanner check, or test subdomain logic locally with scan.localhost.

================================================================================
KNOWN GAPS / FUTURE WORK
================================================================================

1. Scanner account lockout after N failed attempts
   Currently there is no brute-force protection beyond bcrypt's slow hashing.
   For production add a rate limiter on POST /api/scanner/login (e.g., max 5
   attempts per IP per 15 minutes). Use Vercel's KV store or an in-memory
   map with a TTL to track attempts.

2. Real-time guest list updates (Supabase Realtime)
   The current design polls every 10 seconds. For large events where multiple
   doors are scanning simultaneously, Supabase Realtime (subscribe to ticket
   updates for the event) would push updates instantly. Polling is acceptable
   for V1 — add Realtime as an optimization later.

3. Offline support
   If the venue has poor cellular coverage, scans will fail (no network).
   A future enhancement: cache the guest list in memory/localStorage at session
   start, allow offline validation against cached data, sync when connectivity
   returns. Significant complexity — defer until there's a real use case.

4. Multi-door support
   All scanner accounts for an event see the same global scan state. If two
   doors are scanning and person A is scanned at door 1, door 2's guest list
   will show them as scanned after the next poll. This is correct behavior —
   no per-door tracking needed unless the organizer specifically requests it.

5. Scan audit log
   The tickets table already records redeemed_by and redeemed_at. The current
   validate route sets redeemed_by to the string 'scanner'. When scanner
   accounts are active, pass the scanner account username or ID instead so
   you can see which door scanned each ticket.

6. Free event support
   The scanner panel works for paid events. Free events (no Stripe, no orders)
   also create tickets — the scanner should work identically since it reads
   from the tickets table directly, not orders.
